# PowerStep Grid — دليل المشروع الشامل

هذا الملف مرجع كامل للمشروع: إيه هو، إزاي يشتغل، وكل فيتشر اتضاف فيه ومتى ولية.

---

## 1) الفكرة في سطرين

أرضية مولّدة للطاقة من خطوات المشاة (بلاط بيزو/كهرومغناطيسي)، مربوطة بنظام إدارة أحمال ذكي ولوحة تحكم حية بتعرض التوليد والاستهلاك والإشغال ودرجة الحرارة، مع تنبيهات ذكاء اصطناعي (صيانة تنبؤية، تنبؤ بالفجوة). مقدَّم لمسابقة **RoboDam2026**.

---

## 2) حالة كل جزء دلوقتي (حقيقي ولا محاكاة؟)

| الجزء | المصدر | التفاصيل |
|---|---|---|
| **عدد الأشخاص / الإشغال** | 🟢 **حقيقي** (لو الـ ESP32 شغال ومتصل) | عن طريق كود `esp32_probe_csi_combined.ino` — يرجع تلقائيًا لمحاكاة لو الـ ESP32 اتقفل أكتر من 15 ثانية |
| **درجة الحرارة** | 🟡 محاكاة بالكامل | لحد ما يتركّب حساس حرارة حقيقي (DHT22 مثلاً) |
| **الطاقة (توليد/استهلاك/تخزين)** | 🟡 محاكاة بالكامل | لحد ما يتركّب البلاط الحقيقي وحساسات القياس |

النظام مبني عشان أي جزء من دول يتحول لهاردوير حقيقي من غير ما نغيّر بنية الكود — بس نوصّل قراءة جديدة بنفس منطق `/api/ingest` الموجود بالفعل.

## 4) طريقة التشغيل

### أ) الباك اند (السيرفر)

```bash
cd backend
pip install -r requirements.txt        # أول مرة بس
python -m uvicorn app:app --host 0.0.0.0 --reload
```

⚠️ **لازم `--host 0.0.0.0`** — من غيرها الـ ESP32 مش هيقدر يوصل للسيرفر (بيقبل بس اتصالات من نفس اللابتوب).

لازم تشوفي:
```
Uvicorn running on http://0.0.0.0:8000
```

### ب) الداشبورد

في المتصفح:
```
http://localhost:8000/index.html
```

### ج) الـ ESP32 (عدّاد الأشخاص الحقيقي — اختياري)

1. افتحي `esp32/esp32_probe_csi_combined.ino` في Arduino IDE.
2. عدّلي `WIFI_SSID`, `WIFI_PASSWORD`, `SERVER_IP` (IP اللابتوب من `ipconfig`).
3. ارفعي الكود، افتحي Serial Monitor (baud 115200)، واستني رسالة الاتصال بنجاح.
4. تأكيد سريع: `http://localhost:8000/api/status` — لازم `occupancy_source` تبقى `real_esp32`.

⚠️ ملاحظات مهمة اتكشفت أثناء الاختبار الفعلي:
- الـ ESP32 بيدعم شبكات **2.4GHz بس**.
- بعض الراوترات فيها **AP/Client Isolation** بتمنع الأجهزة من التواصل مع بعض — لو الاتصال فشل من غير سبب واضح، جربي تقفلها.
- القناة مثبَّتة على 6 في الكود — لو راوترك مش على القناة دي، ده ممكن يقطع الاتصال.

## 5) الفيتشرز اللي اتضافت بالترتيب — وإيه اللي بتحسّنه كل واحدة

### 5.1) الإشغال الهجين (حقيقي + محاكاة تلقائية)

`simulator.py` بيستقبل قراءة حقيقية من `/api/ingest`، وبيعتبرها "طازة" لمدة 15 ثانية (`REAL_DATA_TIMEOUT_SEC`). لو معدّى الوقت ده من غير تحديث جديد، يرجع تلقائيًا للمحاكاة — كده الداشبورد تفضل شغالة حتى لو الـ ESP32 اتقفل بغلط وسط العرض.

### 5.2) 3 سيناريوهات جول/خطوة (بدل رقم ثابت)

بدل ما نقول "2 جول/خطوة" كحقيقة مؤكدة، عندنا 3 سيناريوهات صريحة يمكن التبديل بينها لحظيًا من الداشبورد:

| السيناريو | القيمة | الأساس |
|---|---|---|
| متشائم | 0.3 جول/خطوة | أقرب لواقع بلاطة بيزو بسيطة |
| واقعي (افتراضي) | 1.0 جول/خطوة | بلاطة كهرومغناطيسية مهندَسة بجودة متوسطة |
| متفائل | 2.5 جول/خطوة | نفس الرقم التسويقي المُعلن لشركة Pavegen التجارية |

**الفايدة:** رد جاهز على سؤال "الرقم ده افتراض ولا قياس فعلي؟" — `POST /api/scenario`.

### 5.3) What-If Slider 🔮 — استكشاف تفاعلي

كارت في الداشبورد: حركي عدد البلاطات المفترَض (1-60) واختاري سيناريو، والاكتفاء الذاتي المتوقع بيتحدث فورًا — **من غير ما يأثر على المحاكاة الحية الشغالة**.

**الفايدة:** بدل عرض ثابت، اللجنة تقدر تجرّب "لو زودنا البلاطات لـ50" بنفسها لحظيًا. `GET /api/whatif?num_tiles=50&scenario=optimistic`.

### 5.4) عزل البلاطة المعطوبة تلقائيًا (Fault-Tolerant)

لما كفاءة بلاطة تنزل تحت 65%، النظام يعزلها فعليًا من حساب التوليد (مش بس تنبيه نصي) — بتظهر في شبكة البلاط بمربّع أحمر مخطّط. أساس منطقي جاهز لربط relay حقيقي لاحقًا.

**الفايدة:** يثبت نضج تصميم Fault-Tolerant حقيقي، مش بس مراقبة.

### 5.5) تنبؤ ديناميكي بالفجوة (Moving Average)

بدل تنبيهات على ساعات ذروة مكتوبة يدويًا، النظام بيراقب متوسط صافي الطاقة لحظيًا ويحسب اتجاه: **تحسّن مؤقت** / **اتساع الفجوة** / **مستقر**.

> ⚠️ ملاحظة صدق علمي: التوليد من الخطوات أصغر بكثير من الحمل الثابت، فصافي القدرة سالب دائمًا فعليًا — "الاتجاه" هنا معناه تحسّن/تدهور نسبي في الفجوة (مثلاً قرب ذروة حركة)، مش توليد فعلي أكبر من الاستهلاك.

### 5.6) توضيح دور الـ buffer + صدق عدّ الأشخاص (في الداشبورد نفسه)

نصوص ظاهرة فعليًا تحت الكروت المعنية:
- **دور التخزين:** "امتصاص نبضات لحظية (ثواني-دقائق)، مش تخزين طاقة يومي كامل".
- **صدق عدّ الأشخاص:** "تقدير تقريبي بعدّ أجهزة الواي فاي القريبة، مش عدّ دقيق للأشخاص".

## 6) فيتشرز كود الـ ESP32 (`esp32_probe_csi_combined.ino` — آخر نسخة)

الكود ده بيدمج طريقتين لاكتشاف الإشغال في نفس الوقت:

### أ) عدّ الأجهزة عبر Probe Requests
الـ ESP32 بيشغّل وضع تنصت (Promiscuous Mode) ويعدّ عناوين الـ IP الفريدة اللي بتبعت طلبات "Probe Request" (أي جهاز بيدوّر على شبكات واي فاي حواليه). كل جهاز اتشاف خلال آخر 60 ثانية بيتحسب "موجود".

### ب) كشف الحركة عبر CSI (Channel State Information)
الشريحة بتقيس تشوّه إشارة الواي فاي نفسها (Amplitude) بسبب حركة الأجسام في المكان — ده بيكشف وجود شخص **حتى لو مفيش موبايل شغال معاه**. النظام بيحسب **Baseline** (خط أساس) في أول 10 ثواني من التشغيل، وبعدين أي تذبذب (Variance) أعلى من الأساس بـ1.5 ضعف يعتبر "حركة".

### ج) منطق الدمج
```
finalCount = deviceCount_                        // ابدأ بعدد الأجهزة
لو (csiPeople > 0 و deviceCount_ == 0): finalCount = 1     // حركة من غير جهاز = شخص واحد على الأقل
لو (csiPeople > deviceCount_): finalCount = csiPeople       // خد الأكبر (احتياطي)
```
عمليًا ده بيطبّق `finalCount = max(deviceCount_, csiPeople)`.

### د) البيانات المُرسَلة لكل حدث
```json
{
  "people_count": 3,          // الرقم النهائي المدموج (المُستخدَم في المحاكاة)
  "device_count_raw": 2,      // عدد الأجهزة الخام من Probe لوحده
  "csi_variance": 0.42,       // قيمة التذبذب الخام من CSI
  "csi_people_estimate": 1    // تقدير CSI لوحده قبل الدمج
}
```
هذه الحقول الإضافية (غير `people_count`) اختيارية في الباك اند — لو مش موجودة، الحدث لسه بيتقبل عادى

## 7) ملفات الـ ESP32 التانية (تاريخ التطور)

| الملف | الغرض | الحالة |
|---|---|---|
| `esp32_people_counter.ino` | عدّ أجهزة بس (Probe Requests) + فلترة متوسط متحرك + توفير طاقة تكيّفي | نسخة أولى، شغّالة، اتستبدلت بالنسخة المدمجة |
| `esp32_csi_udp.ino` | CSI فقط، ببث UDP عالي الأداء (Binary packets) لتسجيل بيانات تدريب موديل | مسار بديل — لو قررتوا تدربوا موديل ML بدل القاعدة الثابتة |
| `esp32_probe_csi_combined.ino` | **⭐ النسخة الحالية المستخدَمة** — دمج Probe + CSI بقاعدة ثابتة، إرسال HTTP مباشر لـ `/api/ingest` | الأحدث والمعتمدة |

---

## 8) أدوات تدريب موديل (لو قررتوا تكملوا في الاتجاه ده)

- `training/csi_udp_logger.py`: يستقبل بيانات CSI عبر UDP من `esp32_csi_udp.ino` ويسجلها CSV بشكل `source,data,ts` (JSON) — متوافق مع نفس شكل ملف RSSI بتاع الفريق.
- `training/train_occupancy_model.py`: يدرّب Random Forest على البيانات دي (بميزات نافذة متحركة زي `mean_amp_roll_std`) لتصنيف مشغول/فاضي.

هذا المسار **منفصل** عن `esp32_probe_csi_combined.ino` الحالي (اللي بيستخدم قاعدة ثابتة بدل موديل مدرَّب). لو حبيتوا تدمجوهم، الموديل المدرَّب (`occupancy_model.joblib`) يقدر يستخدَم في الباك اند بدل عتبة الـ Variance الثابتة.

## 9) مرجع الـ API الكامل

| Endpoint | Method | الوظيفة |
|---|---|---|
| `/api/live` | GET | كل الأرقام اللحظية (توليد، استهلاك، حرارة، إشغال، تنبيهات...) |
| `/api/history` | GET | بيانات تراكمية لرسم الرسم البياني اليومي |
| `/api/status` | GET | فحص سريع: هل البيانات حقيقية من ESP32 ولا محاكاة؟ |
| `/api/ingest` | POST | استقبال قراءة حقيقية من ESP32 — `{"people_count": 3, ...}` |
| `/api/scenario` | POST | تبديل سيناريو جول/خطوة الحي — `{"scenario": "realistic"}` |
| `/api/whatif` | GET | توقّع الاكتفاء الذاتي — `?num_tiles=50&scenario=optimistic` |
